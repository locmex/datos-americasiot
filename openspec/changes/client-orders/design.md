# Design: Client Orders (sistema de pedidos)

## Technical Approach

Feature aditiva sobre el monolito Hono (`index.tsx`). Cuatro tablas relacionales nuevas conviven con el KV. El vínculo con el cliente es soft-reference (`orders.client_id` TEXT → `client:<id>` del KV) con snapshot `client_name`. Acceso relacional vía un cliente service_role reutilizado. RLS deny-all desde el día 1. Frontend: métodos nuevos en `api`/`clientApi`, páginas admin, y primer routing anidado del portal cliente.

## Architecture Decisions

| Decisión | Elegido | Alternativas rechazadas | Rationale |
|----------|---------|-------------------------|-----------|
| Cliente relacional | **Módulo nuevo `supabase/functions/server/db.tsx`** que exporta `db()` (createClient service_role) | Editar `kv_store.tsx` (lo pedía la propuesta) | `kv_store.tsx` está marcado `AUTOGENERATED - DO NOT EDIT`. Tocarlo se pierde en la próxima regeneración. Un módulo aparte replica el patrón `client()` sin riesgo. |
| Vínculo cliente | `client_id` TEXT sin FK + `client_name` snapshot | FK a tabla de clientes | Los clientes viven en KV (`client:<id>`), no en tabla. FK imposible; snapshot preserva historial si el cliente KV se borra. |
| Snapshots en items | `product_name` + `unit_price` copiados en `order_items` | Leer siempre de `products` | El precio/nombre del pedido debe congelarse al momento de la compra; editar el producto no reescribe historial. |
| Borrado de producto | FK `on delete restrict` + check de referencias en endpoint | `on delete cascade` | Un producto en un pedido NO debe borrarse (spec). DB lo bloquea; el endpoint da error legible → usar deactivate. |
| Historial | Tabla `order_status_history` dedicada | Columna JSONB en `orders` | Auditoría append-only, no leída en cada render; consultable por transición. |
| RLS | Enable RLS sin policies (deny-all) | Policies por rol | No hay Supabase Auth JWT (auth casera en KV). Solo service_role toca las tablas; deny-all total es lo correcto. |

## Data Model (orden de creación por FKs)

```sql
-- 1. products
create table products (
  id          uuid primary key default gen_random_uuid(),
  name        text not null check (length(trim(name)) > 0),
  description text,
  price       numeric(12,2) not null check (price > 0),
  currency    text not null default 'MXN',
  status      text not null default 'active' check (status in ('active','inactive')),
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

-- 2. orders
create table orders (
  id              uuid primary key default gen_random_uuid(),
  client_id       text not null,                 -- soft-ref → KV client:<id>
  client_name     text not null,                 -- snapshot
  status          text not null default 'pending'
                    check (status in ('pending','preparing','shipped','delivered','cancelled')),
  carrier         text,
  tracking_number text,
  tracking_url    text,
  notes           text,
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
);
create index idx_orders_client_id  on orders(client_id);
create index idx_orders_status     on orders(status);
create index idx_orders_created_at on orders(created_at desc);

-- 3. order_items
create table order_items (
  id           uuid primary key default gen_random_uuid(),
  order_id     uuid not null references orders(id)   on delete cascade,
  product_id   uuid not null references products(id) on delete restrict,
  product_name text not null,                        -- snapshot
  unit_price   numeric(12,2) not null check (unit_price > 0),
  quantity     integer not null check (quantity > 0)
);
create index idx_order_items_order_id   on order_items(order_id);
create index idx_order_items_product_id on order_items(product_id);

-- 4. order_status_history
create table order_status_history (
  id             uuid primary key default gen_random_uuid(),
  order_id       uuid not null references orders(id) on delete cascade,
  from_status    text,
  to_status      text not null,
  changed_by     text not null,                       -- userId | clientId
  changed_by_role text not null check (changed_by_role in ('admin','client')),
  note           text,
  created_at     timestamptz not null default now()
);
create index idx_osh_order_id on order_status_history(order_id);

-- RLS: deny-all (service_role bypasses RLS)
alter table products             enable row level security;
alter table orders               enable row level security;
alter table order_items          enable row level security;
alter table order_status_history enable row level security;
-- sin policies = ninguna fila accesible para anon/authenticated
```

Rollback: `drop table` en orden inverso (order_status_history → order_items → orders → products).

## Máquina de estados

```
 pending ──(admin)──▶ preparing ──(admin)──▶ shipped ──(client:/received | admin)──▶ delivered ▮
    │                     │
    └──(admin|client)─────┴──(admin|client)──▶ cancelled ▮
```

- `delivered` y `cancelled` = terminales (sin salidas).
- Cliente dispara `shipped → delivered` (`PATCH /client/orders/:id/received`) y puede CANCELAR su propio pedido en `pending`/`preparing` (`PATCH /client/orders/:id/cancel`).
- Admin dispara todo lo demás vía `PATCH /orders/:id/status`, incluida la cancelación desde `pending`/`preparing`.
- Cancelación permitida SOLO desde `pending`/`preparing` (antes de enviar); una vez `shipped`, NO se cancela (sin flujo de devolución en el MVP).
- Validación server-side: mapa `ALLOWED = { pending:['preparing','cancelled'], preparing:['shipped','cancelled'], shipped:['delivered'], delivered:[], cancelled:[] }`. Transición fuera del mapa → 422. Cada cambio inserta fila en `order_status_history`.

## Contratos de endpoints

Prefijo real: `/make-server-ef736a01`. Auth por header `X-IoT-Session`.

### Admin (guard `requireAdmin`)
| Método | Ruta | Request | Response 200 | Errores |
|--------|------|---------|--------------|---------|
| GET | `/products` | — | `{ products: Product[] }` (todos) | 401/403 |
| POST | `/products` | `{ name, price, description?, currency? }` | `{ product }` (201) | 400 validación, 403 |
| PATCH | `/products/:id` | `{ name?, price?, description?, status? }` | `{ product }` | 400, 403, 404 |
| DELETE | `/products/:id` | — | `{ ok: true }` | 403, 404, 409 (referenciado) |
| GET | `/orders` | `?status=&client_id=` | `{ orders: OrderWithItems[] }` | 403 |
| GET | `/orders/:id` | — | `{ order, items, history }` | 403, 404 |
| PATCH | `/orders/:id/status` | `{ status, carrier?, tracking_number?, note? }` | `{ order }` | 403, 404, 422 (transición inválida) |

### Cliente (guard `requireClientSession`, ya existe)
| Método | Ruta | Request | Response 200 | Errores |
|--------|------|---------|--------------|---------|
| GET | `/client/products` | — | `{ products: Product[] }` (solo `active`) | 401 |
| POST | `/client/orders` | `{ items: [{ product_id, quantity }], notes? }` | `{ order, items }` (201) | 400 (items vacío/qty≤0/producto inactivo) |
| GET | `/client/orders` | — | `{ orders: OrderWithItems[] }` (solo del `session.clientId`) | 401 |
| PATCH | `/client/orders/:id/received` | — | `{ order }` | 401, 404, 422 (no está en `shipped`) |
| PATCH | `/client/orders/:id/cancel` | `{ note? }` | `{ order }` | 401, 403 (ajeno), 404, 422 (no está en `pending`/`preparing`) |

**Tipos** (sin type-check en build; contrato explícito por convención):
```ts
type Product = { id:string; name:string; description:string|null; price:number; currency:string; status:'active'|'inactive'; created_at:string; updated_at:string };
type OrderItem = { id:string; product_id:string; product_name:string; unit_price:number; quantity:number };
type Order = { id:string; client_id:string; client_name:string; status:OrderStatus; carrier:string|null; tracking_number:string|null; tracking_url:string|null; notes:string|null; created_at:string; updated_at:string };
```

`POST /client/orders` valida contra `products` (existencia + `status='active'`) y copia `product_name`/`unit_price` a los items dentro de la misma request (snapshot).

## `requireAdmin` helper

En `index.tsx`, junto a `requireClientSession`:
```ts
async function requireAdmin(c: any): Promise<any | null> {
  const session = await requireAuth(c);
  return session && session.role === "admin" ? session : null;
}
```
Uso por ruta: `const session = await requireAdmin(c); if (!session) return c.json({ error: "Forbidden" }, 403);`. Diferencia deliberada con `requireClientSession` (401 vs 403): admin-only devuelve 403 porque la sesión puede ser válida pero sin rol.

## Puente client_id → client_name

Al crear el pedido, el backend lee `const client = await kv.get(\`client:${session.clientId}\`)`; usa `client?.name ?? "Cliente"` como `client_name`. Guarda `client_id = session.clientId`. Si luego el cliente KV se borra: los pedidos persisten con el snapshot; `client_id` queda huérfano (sin cascada, por diseño). El admin sigue viendo `client_name`.

## Map carrier → URL

En `db.tsx` o constante en `index.tsx`:
```ts
const CARRIER_URLS: Record<string,string> = {
  estafeta: "https://rastreositecoreprod.azurewebsites.net/track?wayBill={track}",
  dhl:      "https://www.dhl.com/mx-es/home/tracking.html?tracking-id={track}",
  fedex:    "https://www.fedex.com/fedextrack/?trknbr={track}",
  ups:      "https://www.ups.com/track?tracknum={track}",
};
function buildTrackingUrl(carrier?:string, track?:string): string|null {
  if (!carrier || !track) return null;
  const tmpl = CARRIER_URLS[carrier.trim().toLowerCase()];
  return tmpl ? tmpl.replace("{track}", encodeURIComponent(track)) : null;
}
```
Fallback: carrier desconocido → `tracking_url = null`, se conserva `carrier` y `tracking_number` como texto.

## Routing anidado del portal (Opción B)

Hoy `/portal` tiene solo `index`. Se agregan children y una nav de nivel superior en el layout autenticado de `ClientPortalLayout.tsx` (dentro de `PortalRouter`, bajo `<PortalHeader/>`):

```tsx
// routes.tsx — bajo path:"/portal", Component: PortalRootLayout
children: [
  { index: true,      Component: ClientPortalDashboard }, // Mis Dispositivos
  { path: "orders",   Component: ClientOrdersPage },       // Pedidos (nuevo)
  { path: "login",    element: <Navigate to="/" replace/> },
  { path: "*",        element: <Navigate to="/portal" replace/> },
]
```

Nav de nivel superior (dos `NavLink`: `/portal` end + `/portal/orders`) renderizada en `PortalRouter` justo antes del `<Outlet/>`. Componente nuevo: `src/app/pages/portal/ClientOrdersPage.tsx` (catálogo + crear pedido + historial + marcar recibido). `ClientPortalDashboard` no se toca salvo perder la responsabilidad de "Pedidos".

## Data Flow — crear pedido

```
Portal(ClientOrdersPage) ─POST /client/orders─▶ index.tsx
  requireClientSession → kv.get(client:<id>) [client_name]
  db().from('products').select where id in items & status='active'  [valida+snapshot]
  db().from('orders').insert  → db().from('order_items').insert
  db().from('order_status_history').insert(to='pending', role='client')
  ◀── { order, items } (201)
```

## Data Flow — cambio de estado + tracking (admin)

```
AdminOrdersPage ─PATCH /orders/:id/status {status,carrier,tracking_number}─▶ index.tsx
  requireAdmin → db().from('orders').select(current.status)
  validar ALLOWED[current][next]  (si no → 422)
  tracking_url = buildTrackingUrl(carrier, tracking_number)
  db().from('orders').update({status,carrier,tracking_number,tracking_url,updated_at})
  db().from('order_status_history').insert(from,to,changed_by=userId,role='admin')
  ◀── { order }
```

## Testing Strategy

| Layer | Qué | Cómo |
|-------|-----|------|
| Manual runtime | Cada endpoint (sin type-check en build) | curl/UI: crear pedido, transiciones válidas/inválidas (422), 403 cliente→admin. |
| DB constraints | CHECKs, FK restrict | Insert directo violando price≤0, qty≤0, borrar producto referenciado (409). |
| RLS | Deny-all | Query con anon key → 0 filas. |
| E2E | Flujo completo | Cliente crea → admin prepara/envía+tracking → cliente recibe. |

## Migration / Rollout

Migración `0001_client_orders.sql` versionada en git + aplicada por Supabase MCP (`apply_migration`). Feature 100% aditiva; rollback = `drop table` inverso. Sin migración de datos.

## Resolved Decisions

- **Precios**: SÍ hay precios (`price`/`unit_price` `numeric(12,2)`). Moneda fija `MXN` en el MVP (columna `currency` presente para futuro). Fuera de alcance es SOLO el procesamiento de pagos/facturación (cobros), NO los precios informativos del catálogo.
- **Cancelación**: permitida SOLO desde `pending`/`preparing`, por el admin o por el cliente dueño de su propio pedido (`PATCH /client/orders/:id/cancel`). Una vez `shipped`, NO se cancela (sin logística inversa en el MVP).
